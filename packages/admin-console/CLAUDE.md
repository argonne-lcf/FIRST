# Admin Console

Internal-only React SPA that reads the first-gateway control plane and renders
what's happening. Served in production from behind the **same nginx** as the
FastAPI gateway, so the app and API share an origin.

## Stack

- Vite + React 18 + TypeScript (`type: module`, ESM only)
- Routing: `@tanstack/react-router` (code-defined routes in `src/router.tsx`)
- Auth: Globus (`@globus/react-auth-context` + `@globus/sdk`), PKCE public client
- Fetch client + Tanstack Query: generated by `@hey-api/openapi-ts` (fetch-based with generated queries in `lib/client/@tanstack/react-query.gen.ts`)
-

## Commands (run inside this package dir)

- `npm run lint` — ESLint
- `npm run format` — Prettier
- `npm run check` — Typescript->ESLint->Prettier
- `npm run dev` — Vite dev server on **port 4040** (strict), base path `/admin-console`
- `npm run build` — `tsc --noEmit` then `vite build`
- `npm run gen-sdk` — regenerate the API client from the gateway's OpenAPI

Always run `npm run format` to standardize formatting and `npm run check` to
verify lints/types.

## Regenerating the SDK (`npm run gen-sdk`)

- Pulls from `http://localhost:8000/openapi.json` — **the gateway must be running**
  (`make compose-up` at the repo root brings up the stack on :8000).
- Output goes to `src/lib/client/` — **entirely generated, never hand-edit.**
- Import from: `import { whoamiWhoamiGet, type UserAuthEvent } from "../lib/client"`.

## Auth wiring

`src/lib/api.ts` is the seam between Globus and the generated client.

- `AuthBinding` (`src/lib/AuthBinding.tsx`, mounted in `main.tsx`) bridges the
  live `AuthorizationManager` into the module via `bindAuthorization`.
- `api.ts` calls `client.setConfig({ baseUrl: "", auth: () => <raw access_token> })`.
  - `baseUrl: ""` → same-origin relative requests (matches the nginx deployment).
  - `auth` returns the **raw** token; the generated code adds the `Bearer ` prefix.

Config IDs and scopes live in `src/config.ts` (`AUTH_CLIENT_ID`, `GATEWAY_CLIENT_ID`, `GATEWAY_SCOPE`, `REDIRECT_URI`).

## Using Queries

- All UI components should import query options from `src/queries/`.
- Add the necessary queries to `src/queries`: if it is a trivial passthrough,
  just re-export the generated options (with a cleaner, shorter name) from
  `../lib/client/@tanstack/react-query.gen`.
- The generated functions already contain the `queryKey` (derived deterministically)
  and the `queryFn` that calls the Fetch SDK and throws on errors.
- Use this layer to:
  - Add `select` for shaping/filtering derived data
  - Write queries the codegen can't express — composite fetches, client-side joins, or anything not 1:1 with an endpoint.

```ts
import { queryOptions } from "@tanstack/react-query";
import {
  getWorkflowsOptions,
  getWorkflowOptions,
} from "../lib/client/@tanstack/react-query.gen";

export const workflowQueries = {
  // Pass-through with policy override
  all: () =>
    queryOptions({
      ...getWorkflowsOptions(),
      refetchInterval: 10_000,
      staleTime: 5_000,
    }),

  // Parameterized — forward the typed options object
  detail: (id: string) =>
    queryOptions({
      ...getWorkflowOptions({ path: { workflow_id: id } }),
      staleTime: 30_000,
    }),
};
```

Components never know whether a given query is a thin wrap, a select projection, or fully hand-written

## UI / Styling

Stack: Tailwind v4 + shadcn/ui (Radix-based). No other styling systems.

### Rules

- **Never write vanilla CSS** or add to styles.css (theme variables only).
  All styling is Tailwind utility classes in TSX.
- **Check `src/components/ui/` first.** Before building any UI element,
  see if a shadcn component exists there. Compose existing components
  before writing custom ones.
- **Missing shadcn component?** Install it rather than hand-rolling:
  `npx shadcn@latest add <name>` (e.g. tabs, tooltip, dropdown-menu).
- **Use `cn()` from `@/lib/utils`** for conditional/merged classes,
  never template-string class concatenation.
- **Use theme tokens, not raw colors**: `bg-background`, `text-muted-foreground`,
  `border-border`, `text-destructive`, etc. Never `bg-white`, `text-gray-500`,
  or arbitrary hex values — this keeps dark mode working for free.
- Components in `components/ui/` are ours and editable, but prefer
  variant props (`cva`) over one-off overrides. If you need a new visual
  variant of Button/Badge, add it to the variants definition in the
  component file so it's reusable.

### Layout conventions

- Page shells: `p-6 space-y-6` (or `gap-6` with flex/grid).
- Spacing scale: stick to 2/4/6/8 steps; avoid odd one-off values.
- Data display: use `<Card>` for panels, `<Table>` for tabular state,
  `<Badge>` for statuses, `<Skeleton>` for loading states
  (not spinners or "Loading..." text).
- Status colors: map through Badge variants, defined once in badge.tsx —
  don't scatter status→color logic across pages.

### Imports

- UI components: `import { Button } from '@/components/ui/button'`
- Never import from Radix (`@radix-ui/*`) directly in pages;
  go through `components/ui/`.
